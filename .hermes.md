# Projet — Plateforme d'accompagnement méthodologique du mémoire (Master)

Règles Hermes pour ce dépôt (découverte hiérarchique). Chargé automatiquement quand Hermes
tourne dans ce dossier ou un sous-dossier.

## Référence canonique
- `docs/spec-agent-sujet-v1.md` — SPEC DÉFINITIVE de l'Agent Sujet V1 (source de vérité).
- `docs/architecture-v1.md` — architecture V1 (les 15 points du §42).
- `README.md` — cadrage, stack, méthode, état d'avancement.

## Méthode
- **Un seul agent à la fois.** Ne pas construire les autres agents, l'interface finale,
  ni l'orchestrateur complet (SPEC §4, §41, §44).
- Avant toute implémentation importante : présenter l'architecture et obtenir la validation.
- Pour chaque agent : mission → entrées → processus → sorties → contraintes → vérificateur
  → archi minimale → test → correction → validation.
- Langue : français.

## Contraintes dures
- Stack **Python + FastAPI**. Budget **0 €** : ressource existante → gratuit → open source →
  local → payant (validation humaine uniquement). Aucune activation automatique de service payant.
- Dépendances figées et documentées, aucune installation automatique.
- **Sécurité OWASP LLM01-10** : pipeline
  `LLM → Parser → Schema → Business → Security → composant suivant`. Moindre privilège :
  `read: session_only`, `write: workspace_only`, `delete/deploy/send: false`.
  Isolation par `student_id`/`session_id`.
- Secrets uniquement dans `~/.hermes/.env`. Ne jamais éditer `~/.hermes/config.yaml` à la main.

## Rappels produit
- Sujet ≠ Problème ≠ Problématique ≠ Question de recherche : ne jamais fusionner.
- Ne rien inventer ; marquer `verification_status = "not_verified"` ; questionner plutôt que combler.
- L'agent ne s'auto-attribue jamais `verified` (c'est le rôle du vérificateur).
